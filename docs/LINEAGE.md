## 2. 移動線回來清查時，跑這五條

1. **文字面 diff**：`git diff fork/mobile-T420..master --stat`
   ＋ `git log --oneline fork/mobile-T420..master`（桌面線新增了哪些卡）。
2. **卡面敘事**：`docs/CHANGELOG.md` 從分岔點之後新增的每一條（一卡一行，可 grep 成單一結果）。
   每條的「驗收:」欄記的是**桌面線**的實測值。
3. **資源台帳差**：用 `docs/tools/art_diff.html` 的 `canvasCensus()`（量法寫死在程式碼裡）
   對「移動線版本」與「桌面線 master」各跑一次，比對本文件第 1 節那六個指標。
   ——這是判斷「桌面線的成長會不會壓垮移動端」的唯一可信量法；**不要各自手寫量法**（T419 血淚：
   同一份 BASE 在文件裡出現過三組互不相容的 canvas 數字）。
4. **兩釘**：移動線若動過 `tick`／經濟／AI／RNG 基元，兩釘必然漂移。
   **現行值（2026-08-14 實測，桌面線）：seed301 `pop===3781`（test_fixde.js:4517）／seed22 `pop===4550`（test_fixde.js:6753）。**
   **分岔後已批准的 delta：T432 seed301 4153→3781（孤島電源不併網，業主 2026-08-13 授權重釘）。**
   判準用法：先讀 `test_fixde.js` 的斷言行取現行值（不要用本文件或 ARCH 的抄寫值——T433 實測時兩處都還停在 4153），再比對移動線；不同就先定位是哪張卡的行為改動，再談合併。
5. **存檔相容**：固定城三配方 `rawSave()` 逐位元比對（配方寫在 T420 卡面第 7 節）。
   存檔格式若在任一線被改過，清查必須先解決存檔遷移，其他都是次要。

## 3. 桌面線在清查前要維持的紀律（讓清查便宜）

- **(B) 凍結線的恆等守衛不能拆**：畫布張數／總像素／atlas entries／raw-save bytes ——
  這四類在「只在既有畫布上加蓋」的施工面上數學上不會動，每張美術卡只需一條恆等守衛
  （見 T420／T421 卡面第 6/7 節的兩張表）。**它們同時是移動線的體檢項**。
- **凡會推動 (B) 的卡，CHANGELOG 條目必須明寫增量**（例如「canvas +N 張／+M px」）。
  移動線清查時只要 grep 這些條目就知道要付多少代價，不必重跑全部量測。
- **`index.html` 的檔案大小沒有硬上限**（業主 2026-08-11 明示：「這個項目沒有大小上限」）。
  逐卡**報值**即可（bytes ＋ 相對上一卡的成長），成長率異常時覆核特別確認；
  **不設停止線**。清查時把它當觀察指標，不當閘門。
  > **更正記錄**：本文件原有一條「2.5 MiB 黃線……原本是照移動端顧慮定的，放寬須等清查由業主決定」。
  > 追出處後作廢：唯一源頭是 T419 發卡 commit `b62e785` 卡面第 78 行——
  > 「20 MiB 是不可跨越的格式天花板，**不是手機安全承諾**；若來源大小超過 2.5 MiB，
  > **帳本必標黃並要求覆核特別確認**」，且同節第 68 行自陳整組是「**T419 自訂**的運營上限，
  > 不是宣稱的瀏覽器／格式客觀最大值」。也就是說 2.5 MiB 原意是**報告觸發器**，不是上限；
  > 而「照移動端顧慮定的」這句話**沒有出處、與 T419 原文相反，是覆核方（Claude）自行補的理由**。
  > 語意漂移鏈：T419「標黃」→ T420/T421（Claude 出卡）「停止線候選」→ T425J「必須 <2,621,440 B／
