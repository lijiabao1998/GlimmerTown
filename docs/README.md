# 《微光小鎮》外包開發手冊 — 給 Kimi / DeepSeek 的使用說明

> 這份手冊是給**人**看的：教你怎麼用弱模型安全地繼續開發這個遊戲。
> 模型看的文件是另外三份（見下）。

## 文件地圖

| 文件 | 給誰 | 何時用 |
|------|------|--------|
| `RULES.md` | 模型 | **每次會話都貼**，一字不漏 |
| `ARCH.md` | 模型 | **每次會話都貼**（架構聖經，代碼地圖） |
| `VERIFY.md` | 模型＋人 | 每張任務卡完成後執行 |
| `ROADMAP.md` | 人 | 看長期路線、決定下一張卡 |
| `tasks/T??-*.md` | 模型 | 當前任務卡，**一次只給一張** |
| `CHANGELOG.md` | 模型寫、人看 | 每張卡完成後模型補一行 |

## 標準作業流程（SOP）

1. **開工前（只做一次）**：在 `glimmer-town/` 執行
   ```
   git init
   git add -A
   git commit -m "v1.0 基線"
   ```
2. **每張任務卡**：
   1. 開一個**全新**的 Kimi 或 DeepSeek 會話（不要續舊會話）。
   2. 按順序貼入：`RULES.md` 全文 → `ARCH.md` 全文 → 當前任務卡全文 → `index.html` 相關段落（卡上會說明貼哪幾節；Kimi 上下文長可直接貼全檔）。
   3. 開頭加一句話：**「你是施工工程師。嚴格按任務卡施工，遵守鐵律。先複述你將修改哪些區塊，等我確認後再輸出代碼。」**
      （先複述再動手，能攔下 80% 的理解偏差。）
   4. 模型輸出修改後，人把改動合入檔案，跑 `VERIFY.md` 驗收。
   5. 通過 → `git commit -m "T?? 完成"`，補一行 CHANGELOG，開下一張卡。
      不過 → 把驗收失敗現象貼回同一會話讓它修；修兩輪還不行就 `git checkout -- .` 回滾，這張卡標記 BLOCKED，留給強模型。
3. **絕不並行**：同時只施工一張卡。卡與卡之間的順序見 ROADMAP。

## Kimi 和 DeepSeek 怎麼分工

- **Kimi**（上下文長）：適合需要「通讀整個檔案再小改多處」的卡（如 T01 變體擴充、T03 里程碑）。直接把整份 index.html 貼給它。
- **DeepSeek**（代碼生成較穩）：適合「新增獨立函數/純 sprite 繪製」的卡（如 T02 裝飾物、T05 音效）。只貼卡上指定的段落即可。
- **兩者都不要給的東西**：架構決策、任務拆分、存檔格式設計、「你覺得怎樣更好」之類的開放問題。這些回來找 Claude/Opus。

## 什麼時候必須回來找強模型

- 任務卡連續兩輪修不過驗收（標 BLOCKED）
- 要開新版本階段（v1.2、v1.3…）：需要按當時代碼**重新撰寫**下一批任務卡
- 存檔格式要變、或要動第 5 節（模擬）第 7 節（繪製）的核心邏輯
- 出現「改 A 壞 B」的連鎖問題
