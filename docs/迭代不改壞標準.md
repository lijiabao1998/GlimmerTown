# 迭代不改壞標準（給 GPT／Codex 與所有自主迭代的寫入者）

> 業主 2026-10-10 定：**不管迭代玩法還是美術，都不准迭代壞。** 這份是硬規則，每張卡開工前讀、收工前逐條對（第 8 節自檢清單）。
> 一句話：**每一步都要能證明「沒變壞」；證明不了就停，交給業主，不要繞。**

這份標準的每一條都來自真實踩過的坑（例子寫在條目後面）。它和 `docs/RULES.md`（施工鐵律）、`docs/COLLAB.md`（誰寫哪裡）一起讀；三份衝突時以較嚴的為準，拿不準就問業主。

---

## 1. 開工前（沒做到就不准動手）

1. 讀：本檔、`docs/RULES.md`、`docs/COLLAB.md`、要動的那一區在 `docs/ARCH.md` 的位置、相關的舊卡（`docs/tasks/`）。
2. **先量現況**：改什麼就先量什麼——截圖、數字、守衛跑一次留底。沒有基準，就沒辦法證明沒變壞。
3. **卡面先推**（`docs/tasks/Txxx-*.md`）：目標、**驗收條件（動手前寫好，之後不准改鬆）**、允許觸碰清單、回滾方式。
4. **一張卡只做一件事**。玩法和美術不要混在同一張卡。
5. 開工前 `git fetch`，從最新 `origin/main` 開分支；確認沒有別人正在動同一處。同一時間同一倉庫只有一個人寫 `main`。
6. **能直推 `main` 不代表應該直推**：Codex 雲端雖然被允許直推，仍然一律走「分支 → CI 綠 → PR → 合併」，讓閘門咬得到。

## 2. 玩法迭代不改壞

1. **模擬確定性**：`python tools/verify.py` 的六個哨兵種子必須恆等。改到模擬的卡，卡面要先寫「哪幾個哨兵會變、為什麼」，**業主批准後才准重釘**。
2. **存檔相容**：舊存檔「載入 → 存檔 → 再載入」所有欄位不變；存檔格式只准新增可選欄位（`docs/RULES.md` 第 9 條），否則必須寫遷移與舊檔測試。
3. **平衡數字**：改前改後各跑至少 3 個種子、400 天，**配對比較**（同種子比），寫進卡面；終點差是混沌雜訊，看短視野配對差。會改變玩家體驗的數字（價格、上限、容量）**由業主決定**，不要自己拍板。
   - 例：T597 把殯葬安撫容量改成只數 root，每座墓園 27→3、火葬場 160→40——這種數字必須在卡面寫明、業主裁決、發佈時告訴玩家。
4. **不准用逃生閥或測試開關證明自己沒壞**（守衛不能被逃生閥自證）。

## 3. 美術迭代不改壞

1. **美術定稿權在業主**：新圖先出樣張／對照圖（接觸表最好），業主點頭才接進遊戲；全局觀感（色調、密度、光影、配色）做兩三檔給業主選。
2. **只動業主批准的那幾類**：其他既有像素指紋（`docs/SPR_PINS.json`，`python tools/fp_snapshot.py --check`）**零變動**；有變就是改壞，要嘛修好、要嘛在卡面逐鍵說明並經業主同意。
3. **每張新圖都要有逃生閥**（`?noTxxx` 與 `window.__noTxxx`）能即時退回舊圖；**閥關時整幀畫面與改動前逐位相同**。
4. **必看的狀態**（樣張與真 Chrome 實拍都要涵蓋）：白天、夜裡、冬天（有雪／沒雪）、春夏秋四季色、旋轉四個視角、遠景縮放；以及疊在建築上的層——施工鷹架與樓板線、懸停淡出、倒影、行人、煙、夜燈、招牌。
   - 反例：T601 第一版公園秋天是綠的、鷹架飄在空中、雪下兩層、碼頭背對真水——全是只看了「白天、正常」造成的，靠對抗覆核才抓到。
5. **對標定調**：TheoTown 級密度但分類型不過密；量體高低胖瘦組合；變體要**結構差異**，不是換色。

## 4. 量測與效能：先找原因，不要為雜訊造工具

1. 計時異常，**先在本機用最簡單的 A/B 確認是不是真的**：新舊交錯量、比中位數與 p90、每組 ≥30 樣本；排除已知、與改動無關的週期性成本。確認是雜訊就修判準，**不要為雜訊造追蹤基礎設施**。
   - 例：T602 場景的「暖畫 p95」讓 main 紅，實際新舊圖中位數 2.5 對 2.6 毫秒；那個約 12 毫秒的尖峰是水面每 32 次重畫換一幀、整張地面重建，與新圖無關（T626）。
2. **同一個問題，診斷卡最多連開 2 張**；第 3 張之前必須把已有數據和選項交給業主決定。
   - 反例：T604–T625 連開 20 多張診斷卡追「手機夜景重畫」，每張都死在量測工具本身（追蹤檔超過上限、CPU 剖析時間戳負值、視窗高度改變），一次都沒量到瓶頸；而新圖其實沒有讓重畫變慢，真正的首幀成本在烘圖（T628）。
3. GitHub macOS 跑機的計時**只當參考、不當擋門**（同一份程式 14:51 過、15:25 不過；T630 起它只紀錄）。
4. 效能問題先問「玩家感覺得到嗎」：第一幀卡頓、持續掉幀才是問題；單次尖峰不是。

## 5. 守衛要守對東西

1. 每個守衛寫清楚「它擋什麼壞法」，並用**紅源**證明：故意改壞那一處，**第一個紅燈必須落在目標守衛**（不是別的守衛、不是語法錯誤）。
2. **不准拿被測的東西當標準答案**（循環判斷）：期望值要從獨立來源來——直接烘焙、規格副本、git 物件、線上實物。
   - 反例：T601 第一版用 S21 自己烘的表當答案，四種「只畫第一款／冬天沒換」的壞法全綠；改成逐像素對直接烘焙才擋住。
3. 只有原文釘、沒有行為釘的守衛不算數；行為釘先、原文釘後。
4. **判準放寬一定寫在卡面**：寫明放寬什麼、理由、放過多少。
5. 樣本統計要看清楚它放過什麼：30 個樣本的 p95 只看第二大的那一個，一個尖峰就翻盤。

## 6. 發佈不改壞

1. **main 隨時要綠**。紅了先查原因、修好；**不准帶紅合併、不准用重跑賭過**。
2. 改到遊戲本體（`index.html`／`sw.js`）就要升版本號（`python tools/bump.py <版本>`，並照 `docs/ARCH.md` 現況行、`tools/arch_map.py --fix`、`tools/fp_snapshot.py`）。版本與執行檔雜湊由發佈管線從提交取得（T627 起），**不准再把雜湊或版本號寫死在腳本裡**。
3. 網站只從綠的 `main` 部署；每次合併後確認 Pages 工作流的 `deploy` 與 `verify-published` 綠，並開真網址看一眼。
4. **玩家本機目錄**（`安卓探索\glimmer-town`）只在業主明說後才發佈，一律用 `python tools/merge_bay.py --publish`；任何人不得在那個目錄或埠 8123 跑測試。
5. CHANGELOG 每張卡一行，`驗收:` 欄具名簽核方、不准寫「待覆核」；自己出卡自己施工就如實寫「未經第三方覆核」。
6. 不准 `--force` 推 `main`；推分支寫明兩邊的分支名。

## 7. 停手與回報

1. **同一件事試 2 次沒進展就停**：寫清楚卡在哪、試過什麼、有哪些選項，交業主。
2. **沒跑過的不寫「通過」**；失敗照實寫；卡上「沒做成的事」不准空著、不准美化。
3. 每張卡收工給業主四行內的結論：做了什麼、怎麼證明沒壞、還剩什麼、要業主決定什麼。

## 8. 收工自檢（逐條打勾才准開 PR／合併）

- [ ] 六哨兵恆等（或業主批准重釘）；舊存檔來回不變
- [ ] 既有像素指紋零變動（或逐鍵說明且業主同意）；逃生閥關時整幀相同
- [ ] 美術：日／夜／冬（雪有無）／四季／旋轉／遠景／疊層都看過，對照圖在卡裡
- [ ] 每條新守衛都跑過紅源，首紅落在目標
- [ ] 改了本體就 bump；沒有寫死新的雜湊或版本號
- [ ] `verify.py` ALL GREEN；CI 綠；沒有靠重跑
- [ ] 卡上沒有任何「通過」是沒跑過的
