## 起因

業主批准過的兩批美術（T634、T635）由發佈台架逐位比對「批准提交」守著，但批准提交寫死在三個地方：
- 工作流 `approved-art-release` 的環境變數 `APPROVED_BASE634`（Codex #16 P1：工作流寫死批准提交）；
- `release635.cjs` 第 6 行的 `APPROVED`、`BASE`、`APPROVED_HASH`；
- 兩支台架各自用手寫的逃生閥隔離後來的批次（release634 設 `__noT635`、release635 設 `__noT638`）。新批次的作者得記得去改舊批次的台架，沒改的話新圖會讓舊批次的比對紅，或更糟：新批次沒有逃生閥，舊批次的比對根本隔離不了它。

Codex #17 P1 指出祖先檢查在 squash 合併後必紅；業主已改成只留 merge commit，但錨點仍散在程式碼裡。

## 做什麼

1. `docs/APPROVED_ART.json`：
   - `approved`：每一批的批准提交、`approved/*` 標籤、該提交 `index.html` 的 sha256；T635 另有「批准前的 main」（`base`）。
   - `valves`：每個 `tNNNOn` 批次的逃生閥（`window.__noTNNN`）。
2. `approved/t634`、`approved/t635`、`approved/t635-base` 三個附註標籤，推到 origin（PR 帶不了標籤）。
3. 新 `tools/approved_art.cjs`（兩支台架共用）依序驗：
   - 登記冊等於 HEAD 裡的版本；
   - 標籤指到登記的提交；
   - 該提交的 `index.html` sha256 等於登記值；
   - 該提交是 HEAD 的祖先；
   - **後批規則**：HEAD 裡有、批准提交裡沒有的每個 `function tNNNOn(){`，都要在 `valves` 登記，而且在沙箱裡打開那個閥時啟用函式真的回傳假（Codex #36 P2：原本只看那一行有沒有出現 `!window.<閥>`，寫在註解裡也會過）。回傳這些閥，台架一律打開它們來隔離後批。
4. `release634.cjs`、`release635.cjs` 改讀登記冊：拿掉寫死的提交與雜湊，隔離後批改用登記冊回傳的閥。比對內容與像素相等的要求一字不改。
5. 工作流：刪掉 `APPROVED_BASE634`；validate 加跑 `node --test tools/approved_art.test.cjs`。
6. `tools/scope.py`：
   - `gpt/` 分支不准動登記冊；
   - 改到 `approved`（新增、修改、刪除任一批）要卡頭 `owner_ok`：登記批准就是業主的批准。`valves` 不受限。
   - base 沒有登記冊＝建立（只有本卡）；純 revert 照例免。
7. 文件：AGENTS、COLLAB 衝突配方表、REVIEW-FINDINGS 的 #16／#17 結案。
