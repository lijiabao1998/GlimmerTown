## 0. 這張卡為什麼存在

T434 的夜班調研給出的**頭號建議**是「光照方向統一」，它的根據是從色票表**推得**的
「153 個程序化素材全部右受光」。T434c 用 `art_style.html` 量出 158 左亮／232 右亮，
宣布**推翻**——而 T438 覆核證明那個推翻不成立：**母體與量法都不同**。

- 調研講的母體是 **PAL／mkBld 驅動的程序化素材**，量的是**牆面**的 Δ亮度；
- `art_style.html:109` 取的是 `e.fam==='bld'` 的**全部 390 個鍵**（含約 38 個手繪 HERO_PIX 地標），
  `:88` 量的是**整張 sprite 左右半平面的不透明像素平均明度**（含屋頂、基座、陰影、煙囪）。

T438 已把那句「推翻」撤回，狀態改回 **未判定**，並在卡面寫下「要判它需要另寫**只取牆面像素**的量法」。
**這張卡就是去寫那個量法。** 在有它之前，那條建議既不能據此立卡、也不能宣告已否決——
這種「掛著的未判定」正是最容易被下一個人拿去當現成結論的東西。

## 1. 量法設計（先寫判準，再寫工具）

牆面在哪裡，不用從像素猜——`index.html:1602` 的 `isoBox(g,cx,by,hw,h,cL,cR,cTop)` 本身就是唯一的牆面落筆口：

```
g.fillStyle=cL; for(dx=1..hw)   fillRect(cx-dx, …)   // 左牆面
g.fillStyle=cR; for(dx=0..hw-1) fillRect(cx+dx, …)   // 右牆面
```

而 `:2122` 的主體呼叫是 `isoBox(sg,ax,by,hw,h,wl[1],wl[0],rf)`——
**`cL` 填 `wl[1]`、`cR` 填 `wl[0]`**。所以「牆面受光方向」的真值就是每一次 `isoBox` 呼叫的
`lum(cL)` 對 `lum(cR)`，母體就是**所有 `isoBox` 呼叫**（手繪 HERO_PIX 不走這條路，天然被排除）。

判準寫死在這裡，任何人都能重算：

> 一次呼叫判「右受光」⇔ `lum(cR) > lum(cL)`；判「左受光」⇔ 反之；相等記平手。
> `lum` 用與 `art_style.html` 同一條 Rec.709 係數（0.2126 / 0.7152 / 0.0722，先除 255）。
> 母體＝一次完整建圖裡的全部 `isoBox` 呼叫，逐呼叫計數，並另附「逐鍵取主體那一次」的分族統計。

Δ=`lum(cR)−lum(cL)` 中位 **0.1131**，`|Δ|` 中位 0.1137。

**調研的前提成立**（153 個程序化素材全部右受光——本次量到的是 108 個鍵，
差異來自「一次建圖裡實際走 `mkBld` 的鍵數」與調研當時的口徑，數字以本次實測為準）。
T434c 那句「推翻」是錯的，T438 已撤回，本卡把狀態從「未判定」改成**判定：前提成立**。

**同時量到調研沒講的東西**：真正的不一致在附屬構件——**240 面裡 79 面（32.9%）左受光**，

**本卡不動它們**：那是觀感決定，需要人眼樣張，且應由業主定奪。

### 5.2 母體的定義改過兩次（都寫在這裡，因為錯的那兩版才是這張卡的內容）

1. **第一版：流水帳長度**。兩次跑同一份程式碼量到 **435 與 444**。
   **同一件事量出兩個數字，那個數字就不能引用。**
2. **第二版：等長度不再增長**。等了 20 秒沒等到——因為遊戲跑起來之後素材還會被重建
   （同期流水帳 444 → **1416** 筆還在長）。長度根本不該是母體。
3. **第三版（採用）：相異牆面**。主體逐鍵去重、附屬構件以 `(cL,cR,hw,h)` 去重；
   穩定條件改成「相異數連續 8 次輪詢不變」，實測 **1,750 ms 就穩定在 348**。

順帶查明：`isoBox` 的 100 個呼叫點全部落在 `index.html` 的 1600–10343 行，
繪製區（15218 之後）一個都沒有 ⇒ 那些重建是建圖路徑重跑，不是每幀在畫牆。

### 5.3 歸屬鍵「用過即清」

第一版讓 `__wallKey439` 一直留著，於是主體之後的附屬構件呼叫全被記成同一個鍵，
量具靠「逐鍵只取第一次」擋掉了——**但那是量具在替記錄鉤擦屁股，原始資料本身是錯的，換一支工具就會被騙。**
改成 `isoBox` 取用後立刻清空：主體帶鍵、附屬構件一律 `null`，分族不靠外部約定。
