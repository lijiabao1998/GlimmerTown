## 已驗證的前提（施工者直接採用，不必重推）

- `DIRV = [[0,-1],[1,0],[0,1],[-1,0]]`（`index.html:11725`）＝方向索引 `d∈{0,1,2,3}` 對應世界 **N/E/S/W**。
- `DIRSCR = [[4,-2],[4,2],[-4,2],[-4,-2]]`（`index.html:12005`）＝各方向的**螢幕**向量（車燈、航行燈用）。
- **兩表在 rot=0 下自洽**（已手算）：世界北 `(0,-1)` 的螢幕位移 `Δsx=+32, Δsy=-16` → `(+4,-2)` = `DIRSCR[0]`。
- **方向索引的正確旋轉是 `(d + viewRotEff()) & 3`，不是 `rotMask`**。已用 `w2v` 手算逐項驗證：

  | r=1，`w2v(x,y)=(N-1-y, x)` | 世界方向 | view 位移 | = view 方向 | `(d+1)&3` |
  |---|---|---|---|---|
  | d=0 北 `(x,y-1)` | 北 | `(+1,0)` | 東 = 1 | 1 ✓ |
  | d=1 東 `(x+1,y)` | 東 | `(0,+1)` | 南 = 2 | 2 ✓ |
  | d=3 西 `(x-1,y)` | 西 | `(0,-1)` | 北 = 0 | 0 ✓ |

- **A/B 是螢幕對角線，不是左右朝向**，所以必須跟轉。證據在精靈生成端
  （`index.html:1861-1873` 與 `6655-6754`）：`B` 是 `A` 的水平鏡像（`translate(w,0); scale(-1,1)`），
  而 `A` 的車身是 2:1 階梯（往右走往上抬）＝ `DIRSCR[0]/[2]` 的「右上／左下」對角；
  `B` 鏡像後 = `DIRSCR[1]/[3]` 的「右下／左上」對角。
  ⇒ `(d===0||d===2)?'A':'B'` 的語意是「這輛車躺在哪條螢幕對角軸」，**純螢幕量**。
- **推論**：A/B 在**奇數旋轉互換、偶數旋轉不變**。`mir` 同理。
- **rot=0 逐位元恆等**：`viewRotEff()` 在 r=0 回 0，而所有方向欄位都已查實恆為 `0..3` 整數，
  故 `(d+0)&3 === d`，`&3` 是 no-op。**這是本卡的安全底座。**

## 半修危害（本卡最重要的施工紀律）

**同一區塊內只改一部分，會比現在更難看。**

現況是「整輛車連同車燈都一致地指錯方向」——至少是自洽的錯。
若你只改車身不改車燈，就變成「車身朝東、頭燈打向北」；
只改精細路徑不改 fallback，就變成「有 sprite 的火車轉了、退化模式的沒轉」。

所以：**B1/B2/B3/B4/B5/B6 六組，每一組內部的所有行必須在同一次改動裡完成。**
建議每組算一次旋轉後方向存成區域變數再共用，既省重複呼叫也天然防半修：

```js
const fd = (o.car.d + viewRotEff()) & 3;   // B1，宣告在 if/else 之外
const fd = (o.svcD  + viewRotEff()) & 3;   // B2
const fd = (o.bd    + viewRotEff()) & 3;   // B3
const tdv= (o.td    + viewRotEff()) & 3;   // B4，SPR 路徑與 fallback 各自一份
const sdv= (o.sd    + viewRotEff()) & 3;   // B5
const tv = (o.trd   + viewRotEff()) & 3;   // B6，同上
```

變數名不強制，但**同一區塊只算一次**。

已落地的同型寫法可直接照抄（T375）：
`index.html:12997` `SPR.oneway[((t.oneway-1)+viewRotEff())&3]`、
`index.html:13682` `SPR.plaza.path[(pd+viewRotEff())&3]`。
