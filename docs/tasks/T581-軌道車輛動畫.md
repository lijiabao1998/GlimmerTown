# T581 軌道車輛動畫：車輪旋轉／頭燈光錐／柴油排氣（美術素材強化）

**日期**：2026-09-12　**發卡／施工**：Claude　**車位**：`bay/kimi`　**base**：`69cb6da`／v11.190
**授權**：業主 2026-09-12「下一張直接做Claude，施工紀律必須遵守，但是項目發揮每次最大完成度，開始吧Claude，繼續美術素材强化」
**業主定序**：① 美術風味疊加（**更好的火車動畫**＝他親口點名）② 能跑 ③ 故事深度

## 0. 進場探針：火車不是畫得差，是**沒有幀**

讀 T344c 的 `mkVeh`（index.html:7105）：單節火車已有 **40+ 色塊**——轉向架、四車輪與輪心高光、
等距斜面車身（亮面／暗側／腰線）、個別車窗＋窗框、車頂通風肋、車頭斜鼻＋大前窗＋頭燈、
電車受電弓，外加一張夜間窗燈圖。**靜態品質沒問題。**

問題在於它產出的是 `{A,B,NA,NB}` —— **每個方向恰一張圖**。火車沿軌道滑行時：

- 車輪不轉（輪心高光固定在同一像素）
- 柴油機車不冒煙
- 夜裡有頭燈的「點」，但地面沒有光
- 車停下來（`p` 不前進）時，外觀與全速行駛時**完全一樣**

對照組：專案早有多幀動畫的成熟作法（T152 的 `SPR.windRotor` 4 幀、`SPR.radar` 4 幀、
`SPR.parkFtn` 3 幀、`SPR.warnBlink` 2 幀、`SPR.fire` 2 幀），繪製端以 `visT` 取幀。
**軌道車輛是唯一一類「會動卻沒有幀」的載具。**

### 關鍵設計判斷：幀索引必須由**行進距離**驅動，不是時間

`updTrains` 的車輛物件是 `{x,y,d,p,pt}`，`p` 是本格內的行進進度（`c.p+=dt*1.1`，滿 1 進一格）。
既有動畫全部用 `visT`（時間）取幀——那對風車雷達是對的，**對輪子是錯的**：
時間驅動會讓停住的車輪子照轉。本卡用 `Math.floor(o.train.p*4)&3`，**車停輪停**。

## 2. 手法（四件，全烘焙＋純繪製，零亂數、零模擬改動）

1. **車輪旋轉 4 幀**：`mkVeh` 改為產出 `AF/BF/NAF/NBF` 四幀陣列；輪心高光沿 4 個位置輪轉。
   **`A/B/NA/NB` 保持等於第 0 幀**（向後相容：`__noTrainSpr` fallback、`GV` 測試橋、既有 12 個指紋鍵全不受影響）。
   施工中補一項（接觸表 6× 實拍的誠實回饋）：只挪動 1px 高光在 2×2 輪面上**幾乎看不見**，
   於是加一道對比——高光每兩幀亮一次（`#3d444f`／`#939daa` 交替＝輪輻每轉半圈反一次光），
   f0 沿用原圖的暗高光、不重畫，指紋零變動的設計不受影響。
2. **柴油排氣 4 幀**：僅 `loco:true && !panto`（火車頭，電車不冒煙），車頂小煙隨幀升起淡出。
3. **夜間頭燈光錐**：`carIdx===0` 時在行進方向前方加一段漸弱光池（`nightSprites` rect），取代現行單一 2px 點。
4. **受電弓火花**：電車在 f2 爆閃／f3 餘輝（施工中由 1 幀改為 2 幀——單幀閃一下太像雜訊，
   兩幀衰減才讀得出「電弧」）。日圖先畫亮色、夜圖的發光**落在同一 footprint** 上＝「先有燈具，才有光」。

繪製端幀索引：`Math.floor(o.train.p*4)&3`（電車同理用其 `p`）。逃生閥 `window.__noVehAnim581` 一鍵回到單幀。

## 4. 驗收（檔尾 T581 塊）— 如實記：出卡規劃的 G3/G4 在施工中被拆重組

出卡時把「幀互異」與「差異落在哪」寫成同兩根釘（G3/G4），施工中發現**那是兩種不同的證據，
拿不到同一個地方驗**：Node 的 DOM stub 無像素（T563 G2／T570 G1c 判例），互異性只有真 Chrome 的
CRC 能說；而落點反過來可以在 Node 裡用台架問出來。於是拆成 G4（互異，真 Chrome 基線承接）
與 G9（落點，Node 台架），並因為施工中實踩一個 bug 另生 G8。以下是**實際落地**的釘：

- **G0 前置**：六種軌道車輛 record 皆在場。
- **G1 結構釘**：`AF/BF/NAF/NBF` 皆長度 4、四格是**四個不同的 canvas 物件**、尺寸與本體相同。
- **G2 向後相容釘**（比出卡規劃**更強**）：幀 0 必須是 `A/B/NA/NB` **物件本身**（`===`），
  不只是逐像素恆等——同一物件必然逐像素恆等，而且連 `__noTrainSpr` fallback 與 GV 測試橋的語意都鎖住。
- **G3 清冊收錄釘**：三幀新圖必須進 `sprAtlas356`（`.AF1..3`／`.BF1..3`），幀 0 不得重複入冊。
  不進清冊＝沒有任何像素指紋看著它，而本專案以像素為真相源。
- **G4 四幀指紋互異釘（本卡核心，真 Chrome 承接）**：讀 `docs/SPR_PINS.json`——
  **日圖四幀恰 4 種指紋**（相同＝假動畫）；**夜圖：受電弓車恰 3 種**（f0=f1 無火花／f2 爆閃／f3 餘輝）、
  **柴油車與客車恰 1 種**（正反雙向：車輪不是光源，>1 就是漏光進發光層＝夜裡輪子在發亮）。
  T549 G2b 強制 `SPR_PINS.__meta.ver === GAME_VER`，所以每次 bump 都會逼出一次真 Chrome 重跑，
  這根釘因此拿得到新鮮的像素事實——**但也要如實說：只改 index.html 不重跑 fp_snapshot，本釘咬不到**，
  它守的是「入庫基線必須長這樣」，與 T549 的版本釘互鎖才完整。
- **G5 幀索引由行進距離驅動**（原文釘）：`Math.floor(o.train.p*4)&3`／`o.tram.p`；G5b 不得摻 `visT`。
- **G6 死碼釘**：`__noVehAnim581` 必須在四處（火車／電車的取幀與夜間光錐）真被讀取。
- **G8 落點在畫布內釘（本卡實踩才生出來的釘）**：用產品的同一組幾何常數重算新畫件的最高落點，
  必須落在 `[0,H2)`。第一版把受電弓火花畫在 `my-7`／`my-8`＝**y=-1／y=-8，整張在畫布外**，
  程式不報錯、日圖指紋照樣四幀全異（因為車輪在動），**只有夜圖 CRC 四幀全同洩了底**。
  現在這幾件的最高點恰好貼著 y=0，餘裕為零——G8c 把「餘裕為零」本身也釘住。
- **G9 幀差落點釘（真像素，Node 可跑）**：把產品的幀生成段切片真跑，餵一個 `drawImage` 為 no-op
  的假 canvas，於是「複製幀 0」被吃掉，畫布上剩下的恰是這一幀多畫的東西。斷言：
  客車幀差全在轉向架線以下（y≥11，車頂零差異）且夜圖零差異；柴油機車每幀都要跨到 y<11（排氣）
  且排氣不進發光層；電車 f1 無火花、f2/f3 有且 f2 面積大於 f3；
  **G9j 電車夜圖亮點必須全部落在日圖同幀畫亮的像素上**（0 點憑空發亮）＝T574 G23d 判例搬到載具上。
- **G7 零亂數**（剝註解掃幀生成段；起訖錨唯一性＋段長合理性由 G7a/G7b 先驗，防錨點鏽蝕成恆真式）。

## 7. 施工紀錄

### 7.1 真 Chrome 指紋抓到一件 Node 永遠看不到的事

第一版把受電弓火花畫在 `my-7`／`my-8`。幾何是 `W2=32,H2=22,BODY_Y=9` ⇒ 受電弓頂桿就在 **y=0**，
頭上一格餘裕都沒有；算出來是 **y=-1／y=-8**——**整張在畫布外，一個像素都沒畫到**。
程式不報錯；日圖指紋照樣四幀全異（因為車輪在動）；唯一洩底的是 **夜圖 CRC 四幀全同**
（`trainLoco` 的 `736b0ad6` ×4、`tramVeh` 的 `b02e92c9` ×4）。
Node 的 DOM stub 無像素（T563 G2／T570 G1c 判例），這件事在套件裡看不見。
修法沿用 T574 G23d 判例「**先有燈具，才有光**」：火花落在頂桿自己那一列，日圖先畫亮色、
夜圖的發光落在**同一 footprint**。沉澱成 **G8**（落點）與 **G9j**（夜⊆日）兩根釘。

### 7.2 G9 台架：從「只記落筆位置」到「會複製、會鏡射、會記顏色、會數裁切」

出卡時的台架把 `drawImage` 設成 no-op（用來吃掉「複製幀 0」那一步），量出來的是**落筆 footprint**。
對抗覆核指出這個設計有三個結構性盲點，全部改掉：

| 台架能力 | 它擋住的事 |
|---|---|
| `drawImage` 真的複製 ＋ 底圖先塗哨兵色 | 拿掉「複製幀 0」那一句 ⇒ 哨兵不見（G9a4） |
| `translate/scale` 真的鏡射 | **B 面四幀過去從頭到尾沒被量過**（G9a6/G9a7） |
| 記 `fillStyle` 的顏色與 alpha | 日圖火花改全透明、夜圖照亮＝有光沒燈具（G9j） |
| 數被畫布邊界裁掉的面積 | **任何**落筆畫到畫布外都現形，不只寫死的那六筆（G8） |
| 逐像素比對四幀內容 | 假動畫在 Node 側第一次咬得到，不必等真 Chrome（G9-diff） |

另外 `run9` 餵的 cfg 改成**從產品自己的六個 `mkVeh({...})` 呼叫原文解析**，
不再是測試側手抄一份——手抄的那份會讓釘子驗的是「另一個產品」。

### 7.3 接觸表的誠實回饋：輪子的動畫看不見

6× 放大的接觸表（六車 × 四幀 × 日夜）交給業主。讀得出來的是**排氣**（f1→f3 煙羽上升淡出）
與**受電弓火花**（f2 爆閃／f3 餘輝）；**1px 高光在 2×2 輪面上挪位置幾乎看不見**。
補了一道對比（高光每兩幀亮一次＝輪輻每轉半圈反光，f0 沿用原圖暗高光不重畫）之後才讀得出來，
但仍是輔助性的——這是 32×22 側視圖的尺寸極限，不是實作偷懶。
若要更強的行駛感，下一張可做「車身 1px 顛簸」，但那會動到本卡「只有轉向架以下在動」的契約
（G9c 要重寫），屬業主裁決。

1. **Browser 面板隱藏時分頁被節流**，遊戲 boot 卡在 `pct 2` 永遠不 `ready`，`sprAtlas356()` 回 0 筆、

交付三張：**A 接觸表**（六車 × 四幀 × 日夜，6× 放大）、**B 實景夜間鐵路**（廣角，兩列車在線上）、
