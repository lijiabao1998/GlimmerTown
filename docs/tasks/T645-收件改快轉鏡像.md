## 起因

T640 起落地只有一條路：PR → CI gate → main。本機 `C:\dev\glimmer-town` 的 master 實際上已經只做快轉（`git merge --ff-only origin/main`），但文件和工具還停在 2026-09 的「車位交易」時代：
- COLLAB §9 的收件寫的是「收進車位 → 非作者跑 `merge_bay.py BAY --deploy`」，§8 規則 2 要求觸碰集合相交就強制串行。
- `merge_bay.py --publish` 只查 master 乾淨、verify.py 綠，不查 master 上的東西有沒有經過 CI。master 若多出本機提交（例如 0a2b1d8 那種誤操作，或車位交易產生的整合提交），照樣會被發到玩家目錄。
- `merge_bay.py BAY --deploy` 會把剛在本機做出來、從沒上過 main 的整合提交直接發給玩家。

T644 已經把 CHANGELOG 三道帳本閘搬上 CI，收件這一側不再需要本機另驗，可以簡化。

## 做什麼

1. `merge_bay.py --publish` 加前置檢查：
   - `refs/remotes/origin/main` 必須存在；
   - master 必須是 origin/main 的祖先或等於它（也就是 master 上每個提交都已經落在 main 上、過了 CI gate）；
   - master 領先 origin/main 就紅，訊息說明「先把本機提交推成分支開 PR，落地後再快轉」；
   - master 落後只印一行提示（發佈的是較舊但上過 main 的版本），不擋。
   - 檢查放在凍結 master 之後、跑 verifier 之前，紅了玩家目錄零寫入。
   - 不在 `--publish` 裡 fetch：main 有規則集禁強推，origin/main 只會前進，舊的遠端追蹤 ref 一樣能證明「這個提交上過 main」。
2. `merge_bay.py BAY --deploy` 退役：一開始就拒絕，不建交易、不動 master。整合提交 M 是本機新做的，不可能已經在 main 上，留著它等於前置檢查有一條繞路。`BAY --no-deploy`、`--resume`、`--abort`、`--status` 不變；T645 之前留下的 deploy 交易仍可 resume（目前沒有，`--status` 可查）。
3. COLLAB：
   - §7 開頭標註：車位交易是 2026-09～10 的歷史流程，現行收件是快轉；`--publish` 段補前置檢查。
   - §8 規則 2「強制串行」拿掉，改成「從最新 origin/main 開分支，衝突照 §9 配方解」（T639 已預告）。
   - §9「GitHub → 本機」改寫成快轉配方，並新增「PR 分支的衝突配方」：CHANGELOG、版本號、SPR_PINS、ARCH 現況行、卡頭凍結欄各怎麼解。
4. AGENTS「最常被忘的幾條」加一行：本機 master 只快轉，不在上面施工或合併。

## 紅源

- 工具鏈臨時倉庫：
  - master 領先 origin/main → `--publish` 首紅是新前置檢查（verifier 沒跑、玩家目錄零寫入）；

  - master 等於 origin/main → 綠；落後 → 綠並印提示；

## 放寬了什麼

一處：整合樹不再在 Windows 本機另驗一次。
- **放寬什麼**：落地前不再在本機跑 B／S／M 三道 verify.py（車位交易），收件只快轉。
