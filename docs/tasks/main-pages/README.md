## Release identity (T627)

The seven runtime files are `index.html`, `sw.js`, `manifest.json`, `icon.svg`, `icon-v1-192.png`, `icon-v1-512.png` and `icon-v1-maskable-512.png`. `tools/pages/release-identity.cjs` implements these rules, and every other pipeline script takes its release values from it.

1. **Current release comes from the commit.** Each expected hash is the sha256 of `git cat-file blob HEAD:<file>`. Each working-tree file must be a regular file, not a symlink, and byte-equal to that blob; otherwise the run stops with "Runtime file differs from committed HEAD". When `GITHUB_SHA` is set it must equal `git rev-parse HEAD`.
2. **Version comes from the files.** `const GAME_VER='…'` occurs exactly once in `index.html`, `const APP_VER='…';` exactly once in `sw.js`, and the two are equal. That value is `APP_VERSION`; the main cache name is `glimmerville-main-shell-v` followed by `APP_VERSION`.
3. **The previous release (PREV) is what the live site serves.** The seven files are fetched from `https://lijiabao1998.github.io/GlimmerTown/` with `cache:'no-store'`, no redirects and status 200 only, in up to six tries 1, 2, 4, 8 and 15 seconds apart. The three namespace substitutions are undone; each anchor must occur exactly once. PREV is the newest commit on the first-parent `origin/main` chain whose seven blob ids all match and that is an ancestor of HEAD. Every match carries the same seven blobs, so a runtime-neutral commit that lands on main later does not move PREV off a branch cut before it; if a match exists but none is an ancestor of HEAD, the run stops. Packaging PREV must reproduce the live bytes exactly. Every step fails closed, with no fallback. The scripts fetch the history they need into a shallow checkout themselves. `PAGES_PREV_COMMIT=<sha>` is a local-only override: it is refused in CI and recorded as `override-unverified`. Set it locally when the network to `lijiabao1998.github.io` keeps resetting. In CI a live-lookup failure inside `native-acceptance` cannot be cleared by rerunning that job, because the job allows one attempt only (`GITHUB_RUN_ATTEMPT==1`); it needs a new push or dispatch.
4. **What counts as a release.** If any of the seven source files differ between PREV and HEAD, `sw.js` must differ and the version must be numerically higher (11.99 is lower than 11.100). If none differ, the real-browser upgrade test records `not-applicable-no-runtime-change` and passes.
5. **Baselines come from PREV's git objects.** The browser comparison in `docs/tasks/t603-shots/scene603.js`, run on Linux and, through the native adapters, on macOS, uses PREV's committed `index.html` as the baseline page and PREV's `docs/SPR_PINS.json` as the sprite baseline. A `window.__noT###` escape flag that is new since PREV is switched together with `__noT603`, so a new art card's flag takes part without editing the hash-pinned timing lines. Those legacy comparisons switch T603 off in both documents, so once PREV itself draws T603 the world phase also compares art-on frames: the 16 escape-rig frames and all 308 world scenes of the candidate, with T603 on and only the new escape flags set (`window.__newEscapeOff603`), must equal PREV's art-on frames pixel for pixel. A previous release without T603 (the frozen 329f660 pair) has no art-on reference and is recorded as not applicable. In every phase, the sprite pins of the booted PREV document must also equal the candidate's in the same Chrome, so a pin file committed on main without a runtime change cannot stand in for PREV's sprites.
6. **Frozen history stays frozen.** T603 provenance (the inverse patch, index `99bea3bd…`, rebuilt base `b9190da5…`) is checked only against `4dd0fa4:index.html` by `docs/tasks/t603-shots/native603.js`, never against HEAD.
7. **These checks stay strict and unchanged:** the seven-file allowlist, the regular-file and empty-output checks; the namespace anchors and the round-trip check; the Pages origin and `/GlimmerTown/` path; the foreign cache and storage sentinels; the worker instrumentation anchors and `SLOT_KEYS`; the native blocks, the two filter sites and the no-clip rule; the frozen fixtures (worker `3988245f…`, the 11.211 save golden `67686714…`, the old-save manifest, the seed-22 city); the timing spans and the Chrome launch line; the upgrade gate order; "an upgrade changes only `gameVer`"; `GITHUB_RUN_ATTEMPT==1`; `--min-pass`.
8. **Approval is the merge.** A hash derived from a commit cannot reject that commit, so "approved" now means a commit on main that passed every job the deploy job needs. Still enforced: tested bytes equal committed bytes equal packaged bytes, every job runs the same commit, and only a push to main deploys. Anyone who could push to main could already edit the old hard-coded pins, so the trust boundary was the merge before too.

Test 16 in `tools/pages/release-identity.test.mjs` keeps release values from being written back. It fails if any `tools/pages/*.mjs` or `*.cjs` file, or `docs/tasks/t603-shots/scene603.js`, contains the current `index.html` or `sw.js` sha256 (full, or its first 8 hex digits, in any letter case) or the current version as `'…'`, `"…"`, a backtick string, or `v…`. `native603.js` is not scanned because it is frozen history.

To see the pair a run will use: `node tools/pages/release-identity.cjs --previous --json`.

## Why the package needs separate storage

The existing Lab Pages deployment and canonical main both use `glimmerville.v1`. Repository paths on the same `lijiabao1998.github.io` origin do not isolate localStorage. Publishing main unchanged there could read or overwrite Lab's three slots and preferences.

`tools/pages/build-main.mjs` accepts only the seven main runtime files, each pinned to its committed HEAD blob (rule 1 above). It writes a separate static package with exactly three literal substitutions:

1. Main cloud saves/preferences use `glimmerville.main.v1`.
2. Its SW cache prefix becomes `glimmerville-main-shell-`.
3. Its old generic `gv-v1`/`gv-v2` cleanup list is empty. Activation may delete only caches bearing the new main prefix.

Every output file is verified by reversing those substitutions to the original pinned bytes. Original root index.html/sw.js, GAME_VER/APP_VER, artwork, styles, renderer, simulation and save data format remain unchanged. The local canonical player continues using its existing files and storage keys. There is no automatic migration from the shared Lab namespace.

The namespaces prevent accidental cross-app access; they are not separate browser security origins and still share browser storage quota. Never clear Lab data to make space for main.


The output contains only index.html, sw.js, manifest.json, icon.svg and the three icon PNGs, about4.46MB. Manifest and SW registration retain relative project scope. No game backend, external script or account service is needed.

The workflow defaults to contents:read. Candidate-branch runs perform validation and artifact upload; publication is restricted to a push on main after all four validation jobs succeed. ## Moving an existing local city

The new HTTPS origin cannot see localhost/file saves. In the existing local game, save the desired slot first, then use **匯出分享碼**. On the new site choose an empty destination slot and use **匯入分享碼**. Repeat for each desired slot and keep the exported code as a backup. Export reads the saved slot, not an unsaved in-memory city. This task does not access the user's computer or automatically move any save.

## Publication boundary

Pages serves the main package of the last deployed main commit (see **Release history**); candidate branches do not deploy. The expected project path is `/GlimmerTown/`; the actual HTTPS URL and assets must be verified after deployment. Only the tested main package of the checked-out commit may be published, with its exact commit and hash manifest recorded. Do not publish the repository root, backups, diagnostics or unverified experimental runtime. A new package replaces the live one only after every release job has passed on a push to main for that same commit, and a runtime change must also raise the version (rule 4 under **Release identity**). Until 2026-10-10 this paragraph allowed only the exact approved native T603 seven-file package to replace the live T602 package; that restriction is now history.

The minimum platform configuration is Settings → Pages → Source: GitHub Actions. The owner has repository admin/maintainer permissions in repository metadata, but the available connector does not expose Pages administration and rejects even the Pages read endpoint. Do not infer permission to expand the connector or create a new credential. Resolve the supported settings action with the owner when the concrete candidate is ready.

The deploy job targets the github-pages environment, reads existing configuration with enablement:false, and consumes only the seven-file Pages artifact from the successful package job in the same run. It depends on validate, browser (Linux correctness), package, pages-browser and native-acceptance (the unchanged native timing/liveness thresholds and exact same-browser controls). See tools/pages/RELEASE-ACCEPTANCE621.md for the explicitly approved policy and preserved failed diagnostics (a historical record since T627: its exact-hash approval is replaced by **Release identity** above; its required gates still apply, with the current release and PREV in place of T603 and T602, and its preserved failures stay failures). A separate read-only verification job then tests the actual URL returned by GitHub, with the same pinned package as its expected bytes. Final release checks include actual HTTPS first load, runtime hashes, app-shell completeness, offline saved-city reopen and retained save isolation. An uploaded CI artifact or a completed deployment alone is not a verified playable site.
