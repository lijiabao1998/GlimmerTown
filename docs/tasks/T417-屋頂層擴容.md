## 卡面替你先關掉的四個坑(不讀會多花一輪)

**① 不要試圖在烘焙期讀中心性 tier——結構上不可能。**
`nightTier413` 是 draw 側每遊戲日重建的,`buildSprites` 期城市還不存在(T413b C5 已踩過)。
**用 `lv` 當中心性代理**(T406 已證高 lv 集中於市中心)。

**② 冬季交互是真陷阱,必須處理。**
`snowCap`/`icicleCap` 用的是「逐欄最高不透明像素」找屋頂線,且是 **draw 期惰性計算並快取**
——所以**它們會掃到你新增的屋頂道具**。高瘦道具(天線/煙囪/旗桿)會讓雪線長尖刺、
冰柱掛在天線上。要嘛限制道具高度(建議 ≤6px)、要嘛給 snowCap 排除機制。
**樣張必須含冬季一張**,否則冬天會很醜。

**③ headless 測不到像素——守衛要走「可注入假 sprite」。**
測試環境的 `getImageData` mock 不回真像素 ⇒ `stampRoof` 的屋頂線掃描找不到不透明像素
⇒ 整個函式 early-return ⇒ **T278 現有行為在測試環境是零覆蓋**(T413b D5 已驗明同款)。
你的守衛**不准只有文字釘**(T413b 五次繞過全栽在這)。做法:
- 測試橋:用 `cv()` 造**合成 sprite**(手繪已知屋頂剖面),餵給 `stampRoof`;
- `stampRoof` 內記**落筆決策台帳**(哪個 key、用了哪些道具、幾個、落在第幾段平坦段);
- 守衛斷言台帳,且台帳計數器**經 harness 注入,產品碼零污染**(T416 五輪的成功做法)。

**④ 紅線是什麼、不是什麼。**
本卡**日間幀必然改變**(那就是目的),**不適用**「像素恆等」。紅線是:
- **兩釘 4153/4550 恆等**(烘焙期不碰模擬,套件=機器證明);
- **零亂數**(`kh(key)` 決定性雜湊;禁 R()/ri()/Math.random/vri);
- **烘焙期一次性、每幀零成本**(T413b 的 N² 慘案不得重演——本卡不准在 draw 側加迴圈);
- 不碰 `isoBox`(100 處呼叫點)、不碰牆面(HERO_PIX 手繪禁區=鐵律11,屋頂才是安全加蓋面);
- 開機時間:`stampRoof` 每鍵一次 `getImageData`,鍵數由 ~112 增至 ~200 量級,
  **量測開機耗時並入卡**(超過 +300ms 要提對策)。

## 守衛的攻擊面維度(**驗收條款,不是建議**)

T416 五輪的教訓:**你的釘傾向剛好覆蓋被點名的那個案例,不多一格**(說「兩站三案」就造兩站三案、
說「補兩車」就釘兩車)。本卡因此把維度直接寫進條款——**每一條行為釘都要跨下列維度取樣,
不得只用單一範例**:

| 維度 | 必測取值 |
|---|---|
| 族別 | R / C / I / 服務(H,P,F) / 市政 各至少一案 |
| lv | lv1 / lv2 / lv4(**含新開的 lv4**) |
| 平坦段 | 單段 / 多段(≥2 段皆須落筆) / 窄段(<10px 不落筆) / 超寬段(≥40px) |
| 道具數 | 0(窄段) / 1 / 中 / **上限**(驗上限真的是上限) |
| 變體 v | v0 **與** v11(不得只測 v0) |
| 逃生閥 | 開 / 關兩態 |
| 季節 | 夏 / **冬(雪帽交互)** |

**破壞性案同理**:每案除了「被點名的那個形狀」,再加一個**剛好在釘邊界外一格**的變體
(例:密度上限釘若寫 `n>=3`,就再測 `n===2` 的繞過;族別釘若只驗 R/C/I,就再測「只砍服務族」)。
