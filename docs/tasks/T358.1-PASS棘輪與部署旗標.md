# T358.1 — PASS 單調棘輪＋部署旗標明示

## 出卡背景

T358（工具鏈交易安全）併入後，四方覆核達成共識：verify 閘門還有兩個
「不紅但退化」的洞，以及一個隱式決策點——

1. `verify.py` 只有 `MIN_PASS = 1902` 災難線。bay 相對 base **刪了測試**，
   只要總數仍 ≥1902 閘門照樣綠。
2. 整合作業（M）解衝突時**漏接 bay 的新增斷言**，同樣只要 ≥1902 就進 master。
3. `merge_bay.py` 的部署決策是隱式的：不帶 `--deploy` 就靜默不部署，
   玩家目錄停留在舊 runtime，無任何提示。

設計尺度經兩輪討論收斂（否決項見下）：**不加理由持久化、不擴充交易記錄
schema、不做 `--allow-pass-drop`**，只加兩個比較和一組互斥旗標。

## 設計定案（已拍板，不得再擴 scope）

### ① PASS 棘輪

```text
PASS(S) ≥ PASS(B)    交易發起階段：incoming bay 不得比 base 少測試
PASS(M) ≥ PASS(S)    晉升前階段：整合結果不得漏接 bay 的斷言
```

- 三個計數皆由**同一把尺** `verify.assess_suite` 量出：B 對凍結 base OID、
  S 對凍結 source OID、M 對整合 merge OID，各自在對應 worktree 實跑套件。
- 計數是凍結 OID 的純函數 → **不持久化、不改 state schema**；
  `--resume` 重跑時從凍結 OID 重算，結果必然一致。
- 任一比較失敗 → `ToolError`，master 不動，走既有 `--resume`/`--abort`。
- `MIN_PASS = 1902` **保持不變**，繼續當災難級最低線，不隨版本更新。

### ② 部署旗標明示

- **每次發起 merge**（start 路徑）必須二選一：`--deploy` 或 `--no-deploy`，
  argparse mutually exclusive，缺了直接報錯。**一律強制**，不做
  「觸及 runtime 才要求」的條件分支。
- `--no-deploy` 印出醒目警告：玩家目錄將停留在舊 runtime。
- `--status`／`--abort` 不受影響；`--resume` 沿用 state 已存的
  `deploy_requested` 布林，不再問旗標。
- 不加理由欄位、不改 receipt、不動 journal 格式。

### ③ 不做 `--allow-pass-drop`

目前無真實需求，做了只是提前開一條閘門繞行路。真遇到合法刪測試
（如整卡退役）時**獨立立卡**處理。

## 施工清單

1. `tools/merge_bay.py`：
   - start 路徑加 `--deploy`/`--no-deploy` 互斥必填；`--no-deploy` 警告文案。
   - 交易發起階段實跑 B、S 兩份套件並斷言 `PASS(S) ≥ PASS(B)`。
   - 晉升前（既有 M 驗證點）斷言 `PASS(M) ≥ PASS(S)`。
   - 錯誤訊息帶出兩側實測數字（如 `PASS(S)=1930 < PASS(B)=1947`）。
2. `tools/test_toolchain.py` 追加四類故障注入（沿用 T358 風格）：
   - S 比 B 少一條測試 → 交易拒絕，master 不動。
   - 解衝突漏接新增斷言（M < S）→ 晉升被擋，master 不動。
   - 發起 merge 不帶部署旗標 → CLI 報錯。
   - `--deploy` 與 `--no-deploy` 同帶 → CLI 報錯。
3. `docs/CHANGELOG.md` 頂部追加一條（含否決方案與否決依據）。

`tools/verify.py` 預計**不動**（`assess_suite` 已可 import 重用）；
若實作中發現非動不可，限最小改動並在 CHANGELOG 說明原因。

## 不變量

1. T358 全部既有行為不變：30 例故障注入測試必須保持全綠。
2. 棘輪失敗、旗標缺失時 master 一律不動，證據（state/journal）保留。
3. 閘門 fail-closed：量不到 PASS 數（套件例外、輸出格式異常）視同失敗，
   不得預設放行。
4. 不新增任何「降標準」路徑（無 `--allow-pass-drop`、無理由繞行）。

## 驗收清單

1. `python tools/test_toolchain.py`：既有 30 例＋新增 4 例全綠。
2. 破壞性證明：四類故障各實注一次，確認擋在預期階段且 master 未動。
3. 真實 rehearsal：對真實 bay（乾淨、純 behind）跑一次完整交易，
   兩個棘輪比較皆實際執行並印出數字。
4. CHANGELOG 頂部一條，記否決方案（理由持久化／交易記錄擴充／
   `--allow-pass-drop`／runtime 條件式旗標）與否決依據。
5. 提交前 `python tools/verify.py` 全綠；合併走
   `python tools/merge_bay.py codex --no-deploy`（純工具卡，順便當
   新旗標的首次實戰）。

## 合併順序（專案級約束）
