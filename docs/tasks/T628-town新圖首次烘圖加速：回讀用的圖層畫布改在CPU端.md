## 量到的事實（2026-10-10，本機真 Chrome，有 GPU，seed22 難度 3 長 420 天）

- 新圖讓「已經烘好之後」的每幀重畫變慢嗎？**沒有**：手機／桌面 × 白天／夜，新圖開關的暖重畫中位數差都在 1 毫秒內（T626 卡面）。
- 新圖真正的成本在**第一次畫**：園區新圖是看到才烘（快取起來之後就快），清快取後第一幀要烘幾十張。逐類計時，大頭是 **T601 的垃圾場（k8）**：一張 76–520 毫秒，佔第一幀烘圖時間的一半到七成；其次信仰中心、溫室、大農場各 20–45 毫秒。
- 原因：垃圾場的描邊（`sEnd`／`sEndClip`）每一層都用 `getImageData` 把整張圖層讀回 CPU 判斷哪裡要描邊。圖層畫布預設在 GPU，每讀一次就要等 GPU 做完、再整張搬回來；一張垃圾場有好幾層。民宿（k81）的 `flatten` 同一個做法。
- 試改：這兩種圖層畫布建立時加 `willReadFrequently: true`（瀏覽器就把它放在 CPU 端，讀回不用等 GPU）。真 Chrome 對照 6＋6 張烘圖（垃圾場、民宿 × 三款 × 日冬，圖與夜圖）**逐像素雜湊全部相同**；烘圖時間垃圾場 27–79 → 15–47 毫秒、民宿 6–9 → 2–3 毫秒。

## 做法

1. `art601_k8` 的 `S0`（描邊圖層）與 `art601_k81` 的 `layer()`：`getContext('2d')` → `getContext('2d', { willReadFrequently: true })`。只有這兩行；畫法、顏色、順序一個字不動。
2. 這兩個圖層只是烘圖時的暫存，最後都畫進一般（GPU 端）的成品畫布；遊戲每幀畫的是成品，不受影響。
3. 其他 105 處 `getImageData` 多在開機時的精靈建造（S7–S13 等），影響的是開機時間不是遊玩中的卡頓，本卡不動（另記）。
