# T358 — 工具鏈交易安全

## 目的

把 T352 的「一鍵合併」從順利路徑自動化，升級為可對抗崩潰、衝突、
併發施工與部署失敗的機械閘門。任何驗證程序異常退出都必須判紅；
任何待驗證整合都不得先寫入 `master`。

## 允許觸碰

- `tools/verify.py`
- `tools/merge_bay.py`
- `tools/test_toolchain.py`
- `docs/COLLAB.md`
- `docs/CHANGELOG.md`
- 本任務卡

## 禁止觸碰

- `index.html`
- `sw.js`
- `test_fixde.js`
- `atlas.html`
- `manifest.json`／圖示／任何素材
- 玩家部署目錄
- `master`、`bay/kimi` 與其他 worktree

## 不變量

1. 驗證綠燈必須同時滿足：
   - `index.html` 內嵌腳本、`test_fixde.js`、`sw.js` 語法皆成功；
   - Node 套件 `returncode == 0`；
   - `FAIL:` 行數為 0；
   - `PASS:` 行數不少於當前基線 1902；
   - 正常完成標記存在；
   - CRLF=0、GAME_VER/APP_VER 同步、亂數釘定哨兵仍在。
2. `verify.py` 不得在專案內建立固定名稱暫存檔。
3. 合併前必須驗證：
   - 腳本從 canonical master worktree 執行，當前分支為 `master`；
   - master 與來源 bay Git 查詢成功且工作區乾淨；
   - bay worktree 的分支、HEAD 與 `refs/heads/bay/<name>` 完全一致。
4. incoming commit 先合入獨立 integration worktree；整合後驗證全綠之前，
   `master` HEAD、玩家部署與其他 bay 必須逐位元／逐 ref 不變。
5. 衝突或整合驗證失敗時保留 integration worktree，提供可達的
   `--resume <bay>` 與顯式 `--abort <bay>`；resume 前若 master 已前進必須停。
6. 全綠後只允許以 `--ff-only` 推進 master。
7. 部署必須先在目標目錄持久建立 journal，之後才寫舊檔備份與新檔 stage，再依
   `index.html` → `sw.js`（SW 最後）的順序逐檔原子替換。發布失敗且回滾寫入成功時，
   兩檔須立即恢復為部署前位元；若回滾本身失敗，必須保留 journal，待故障解除後由
   resume 恢復，不得假稱已回滾。程序被強殺／斷電留下的 mixed 狀態須在下次啟動
   自動恢復。誠實邊界：兩個檔名之間仍存在 HTTP client 可讀到混版的毫秒級窗口。
   部署來源必須取自 verified M 的 Git blobs，不得逐檔讀取可變的 master 工作樹；
   all-new 狀態必須先逐檔驗證 live bytes 等於 exact source OID 的 Git blobs，再持久寫入
   該 OID＋兩檔 expected hash receipt，最後才清除 journal。receipt 驗證端也須重讀
   source OID blobs，拒絕手造 receipt 以錯誤 bytes 自圓其說。
8. 回同步 bay 只允許 clean 且純 behind 的 worktree 使用 `--ff-only`；
   dirty、ahead、diverged 一律不改動並明確列為 skipped。
9. `atlas.html` 是施工工具，本卡不部署它。

## 必須具備的故障回歸

- Node 非零退出且沒有 `FAIL:`，驗證必須紅。
- PASS 少於 1902，即使 exit 0／FAIL 0，也必須紅。
- `git status` 查詢失敗不得被當成 clean。
- bay path HEAD 與 bay branch ref 不一致時不得合併。
- integration 衝突／驗證失敗時 master HEAD 不變。
- resume 前 master 前進時不得落後基底硬推。
- ahead／diverged bay 不得被自動 merge。
- 第二個部署檔替換失敗時，第一個檔必須回復原位元。
- 第一檔已替換、程序硬中斷留下 journal 時，下次啟動必須把兩檔恢復為 old。
- journal 必須早於四個 artifact 寫入切點；任一切點硬中斷皆可由 all-old recovery 清理。
- all-new／journal unlink 切點硬中斷時，receipt 必須先於 journal 消失且可冪等續接。
- 有效 source OID 搭配錯誤 live bytes 或偽造 hash receipt 都必須判紅且不得覆寫既有 receipt。
- 發布與回滾同時失敗時須保留 journal，下一次正常 resume 能恢復兩個 old 檔。
- cleanup-pending 的 committed runtime 若晚到回到兩個 old，resume 必須退回 deployed=false
  並重發 exact verified OID，不得卡在假 committed。
- integration branch 在驗證後被推進時，master 仍只能落在 frozen M。
- worktree 已清掉但 branch/state 尚在時，`--resume` 必須能冪等完成清理。
- 偽造 state 不得讓 `--abort` 指向真 bay；偽造 journal 不得碰 atlas 或較新 runtime。

## 驗收

1. `python -B -m unittest tools.test_toolchain -v` → 30/30（`-B` 防驗收本身留下 `__pycache__`）
2. `python tools/verify.py` → 1902+ PASS／0 FAIL／exit 0
3. `git diff --check`
4. T358 提交不得寫入 master、其他 bay 或玩家部署目錄（施工期間 master 可由另一位單寫者前進）
5. 不執行真實 `merge_bay.py <bay>`；交易流程只在臨時測試倉庫驗證

## 回滾

本卡只涉及工具與文件；若任一故障回歸無法穩定重現或完整通過，回退本卡所有
改動，不得以降低 PASS 基線、刪測試或放寬 fail-closed 條件換取綠燈。
