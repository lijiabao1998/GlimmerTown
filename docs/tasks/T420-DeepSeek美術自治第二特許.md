## 2. 施工白名單（唯一可改處）

**產品碼**：`index.html` 的 `buildSprites` 尾端**單一**受管區
`/* ===== T420 ART-LOOP 靜態加蓋 pass ... ===== */ … /* ===== T420 ART-LOOP 靜態加蓋 pass END ===== */`

位置硬性契約：
- 必須在 **T413b 夜之城烘焙完整結束之後**——錨點請用**整段 else 分支的完整字面**
  （`}else{window.__t413BakeCount=0;window.__t413BakeByKind={R:0,C:0,I:0,P:0,H:0,F:0,D:0,S:0};}`）的結束位置，
  **不要**用 `lastIndexOf('__t413BakeByKind')`：該字串在 if 與 else 兩個分支都出現，
  T419 的位置釘因此被「把 pass 搬進 else 分支」騙過（實測 M9：位置釘 PASS，只有白名單釘偶然咬到）。
- 必須在 `R=__savedR;` **之前**。
- 只准對**既有** `SPR.bld[key].img` 落筆日間像素；不得建立／刪除任何 SPR 鍵；不得改 `w/h/ax/ay/sc/night`。
- **pass 內不得有任何條件分支**，除了 `if(sp&&sp.img)` 這種存在性檢查。
  （T419 實測 `if(quality===0){}else{...}` 可讓低畫質玩家完全看不到美術而套件全綠；
  `quality` 由 `localStorage[SAVEKEY+'.q']` 持久化，玩家真的可以是 0。）
- **不得使用計算屬性存取**（`sp['nig'+'ht']`、`sp[k]`）——T419 實測這是繞過所有字面掃描的通道。
  pass 內允許出現的成員名只有 `img / getContext / fillStyle / fillRect / ax / ay / w / h`（`w/h` 只讀）。

**其他可改檔案**：`test_fixde.js`（本卡守衛）、`docs/tasks/T420-*.md`（帳本）、
`docs/CHANGELOG.md`（一行）、`docs/ARCH.md`（版本／行數／PASS 同步，僅在 release tail）。
以上之外任何檔案的任何一行改動 ⇒ 覆核直接退修。

## 3. 六條硬前置（違反即退修，不接受「機器綠」抗辯）

### 前置 A — 先量測，後落筆

每個目標鍵、**每個變體**在動手**之前**，必須先產出並貼進帳本：

1. **確認該鍵的最終生成點**：全檔 grep 該鍵名，列出**所有**生成／覆寫點，取**最後一個**。
   T419 就是死在這一步——讀到 `5424` 的程序化版，漏掉 `8004` 的 HERO_PIX 覆寫版。
   若最終生成點走 `drawHeroPix`，該鍵屬 **HERO_PIX 鍵**，適用前置 F。
2. `w / h / ax / ay / sc / 有無 night`
3. **完整色票**（原色 × 像素數，全列不截斷）
4. **重點細節色清單** ＝ 像素數 ≤ 16 的所有顏色，含每個像素的絕對座標與相對 `ax/ay` 座標
5. **主色逐列 run**（每列的 `x0-x1` 區間）——用來讀出該面的等角走向與既有節律（pitch）

工具已備：`docs/tools/art_diff.html`（本卡附，用法見第 8 節），量測模式一行指令出全表。
**沒有量測表就落筆 ⇒ 該輪整輪作廢**，不接受事後補量。
**變體不得共用一組座標**：`26_1_1/26_1_2` 與 `26_1_0` 的 bbox、色數（9 vs 28）、塔寬都不同。

### 前置 B — 等角走向鐵律

本專案是 2:1 等角。落筆前先回答「這條線屬於哪個面」：

- **地面／屋頂／板面上的線**（板縫、磚縫、分隔線、田壟）必須沿 `(dx=2, dy=+1)` 或 `(dx=2, dy=-1)` 前進。
  一條螢幕水平線或螢幕垂直線**不是任何一個等角面上的直線**。
- **只有真正垂直於地面的細長物件**（塔柱、旗杆、圍欄立柱、煙囪）可以是螢幕垂直線，
  且必須交代落地點與頂端收頭，否則讀成浮空。
- **新增的重複元素必須對齊既有節律**：T419 的桁架 pitch=14 撞上既有法蘭環 pitch=16，
  偏移逐段擴大 2/4/6 px，視覺上是三組「差一點沒對齊」的重複橫帶。先量既有 pitch，再決定新 pitch。

### 前置 C — 重點細節零覆蓋（機器可守）

**禁止覆蓋任何「該鍵原本像素數 ≤ 16」的顏色。** 那一類顏色就是刻意的細節：
航警燈、指示燈、警示黃、白色反光條、單像素高光。它們像素少，最容易被大方塊誤殺，也最傷辨識度，
而且在 CRC／metadata／bbox／存檔位元／PASS 數上**全部驗不出來**。

- 每輪必須用 `art_diff.html` 對照模式跑出「被覆蓋的原色（完整分佈）」，
  任一項落在 ≤16 px 的顏色上 ⇒ **該輪退修**。
- 若某個細節**確實應該被取代**，必須在帳本**逐色申報**：原色、原像素數、覆蓋數、取代後的新表現、為什麼更好。
- **本卡必須新增守衛把這件事釘成機器紅線**（見第 5 節第 3 條）。

### 前置 D — 像素證據只認真實瀏覽器；驗收語言必須與觀測能力對齊

- **每輪必交 `art_diff.html` 對照模式的真實瀏覽器輸出**（貼進帳本）。無此輸出 ⇒ 該輪不予採計。
- 原文釘只能被記述為「拼寫／位置**前哨**」；`push` 型自報橋只能被記述為「**作者申報**」。
  **不得**把任何原文釘或自報橋記述為「像素已驗」「白名單已守」。（T419 的④訊息寫「pass 只可落筆…」
  但在「一筆都沒落」的突變下照樣印 PASS。）
- 帳本每一項證據旁必須標註它的觀測來源：`原文釘` / `自報橋` / `Node 行為釘` / `真實瀏覽器像素`。

### 前置 E — footprint 自夾擠

`clipBase`（index.html:9084-9110）在 pass **之前**執行，pass 之後**沒有人再裁**。
所以 pass 自己必須保證每一筆落筆滿足 footprint 菱形條件：

```
對 sz>=2 的鍵：只允許在  y <= ay  且  |x - ax| <= 2 * (ay - y)  的像素上落筆
```

等價做法：在 pass 尾端對本輪白名單鍵各做一次與 `clipBase` 同式的裁切（只作用於 `img`，`night` 不碰）。
**必交證據**：`art_diff.html` 的「新增不透明（剪影溢出）」與 `sprFootAudit below` 前後值，
兩者都必須**與 base 相等**（T419 實測 below 0→80，兩個懷疑者以不同方法各自算出同一個 80，即為退修）。

> **`sprFootAudit` 在 Node 下的值一律無效。** harness 的 `getImageData()` 只回 4 bytes，
> 於是 `d[...]<24` 對絕大多數像素是 `undefined<24`＝false，**每個像素都被當成不透明**。
> 覆核方用純幾何重算「136×150／ax68／ay148 的全不透明畫布」得 `below=2414 / belowMax=35`，
> **與 Node mock 的輸出逐位相同**——證明那個數字只是畫布尺寸的函數，與畫了什麼無關。
> T419 的 R00 只存了 `{"ok":true,"entries":65}`，其中 `ok:true` 還是**硬寫字面量**。
> 本卡的 footprint 證據**只認真實瀏覽器**。

### 前置 F — HERO_PIX 手繪像素不可覆蓋（鐵律11）

若目標鍵的最終生成點走 `drawHeroPix`（`HERO_PIX` 表在 index.html:1510 起），
則該鍵的**手繪像素是禁區**（鐵律11：牆面是 HERO_PIX 手繪禁區，屋頂／地面才是安全加蓋面）。
可加蓋面只有：手繪剪影**之外**的地面／屋頂區、以及既有的可加蓋環（如 k26 的 `K=#b6bcc4` 法蘭環附近）。
**必交證據**：把 pass 的落筆逐筆分類為 `onHero / onPlate / offSilhouette`，`onHero` 必須為 **0**
（T419 的 26_1_0 是 105 px、25_1_0 是 283 px）。
