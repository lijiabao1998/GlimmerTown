## 起因

CHANGELOG 的三道帳本閘只在本機 `merge_bay.py` 收件時跑：
- 簽核欄（`assert_signoff_landed`）：新條目的「驗收」欄不准含「待」，要寫出 Claude、Kimi、Codex、Grok、DeepSeek、業主、GPT 其中一方；
- 只增不減（`assert_changelog_only_grows`）：刪條目要在提交訊息用 `CHANGELOG-CORRECTION:` 逐條點名；
- 整合不准丟條目（`assert_integration_keeps_changelog`）：合併後的 CHANGELOG 必須保有原本的每一條。

所以 T634 已經上線，到 10-13 收件時才被簽核閘拒絕，只好另開 PR #18 補紀錄。T645 要把收件簡化成快轉鏡像，這三道閘得先搬上 CI，不然一簡化就沒人檢查了。

## 做什麼

1. 新 `tools/landing_gates.py`：三道閘抽成純函式，輸入是 diff 文字、提交訊息、兩版 CHANGELOG 文字，不碰 git、不碰設定。CLI `--base --head` 直接吃兩個 git 物件，給 CI 用。
2. `merge_bay.py` 改成呼叫同一份函式。git 呼叫留在 merge_bay（工具鏈測試會注入假的 runner），錯誤訊息一字不改，行為不變。
3. CI：在 scope job 加一步跑 `landing_gates.py`。工具優先取 base 的版本，免得 PR 改寫自己的檢查。
   - 原計畫寫放在 validate；改放 scope，因為 scope 已經算好 BASE，文件道與 full 道都會跑，gate 在兩道都要求 scope 綠。CHANGELOG 是 `.md`，只改它的 PR 走文件道，也照樣要被查到。
4. 語意不改：
   - 驗收欄不准含「待」、要寫出簽核方之一；
   - 刪條目要逐條宣告；
   - 合併後不准少掉 base 的任何一條。

## 紅源

- 工具鏈的臨時倉庫測試，每條首紅都要落在目標上：
  - 刪 CHANGELOG 一行 → 刪除未宣告；
  - 宣告了刪另一條 → 照樣紅（逐條點名）；
  - 新條目驗收欄寫「待覆核」→ still pending；
  - 沒寫簽核方 → names no reviewer；
  - 沒有驗收欄 → no 驗收 field；
  - 整合時丟了 base 的條目 → 紅。
- 突變：每條規則改鬆，對應測試要紅。
- CI 實跑：推一個「新條目驗收欄寫待覆核」的提交，看 scope 紅在帳本閘，看完 revert。
- 工具鏈既有的 merge_bay 測試照綠：證明抽函式後本機收件行為沒變。

## 驗收

- 本卡 PR 的 gate 綠；CI 紅源如實記錄。
