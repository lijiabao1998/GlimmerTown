# T544 編輯器匯出的是上一局的城市（匯出即所見）

**日期**：2026-08-20　**發卡**：Claude（業主授權：自己玩→出卡→施工→合併）

## 0. 實測（編輯器＋自訂場景 end-to-end 首次全程走通）

這條玩家流程（建圖→設目標→匯出碼→朋友匯入→開玩→勝負）從沒人完整玩過。真瀏覽器 DOM 驅動
（stub prompt/clipboard、點真按鈕）走一遍：

- **核心閉環全通**：目標 UI（人口 30／期限 250／資金 4000）→ 匯出（egoal 正確打包）→ 匯入
  （customScenario 生效、起始資金 4000 套用、diff 強制標準）→ AI 代玩第 9 天 pop 36 達標＝勝利路徑 ✓；
  期限 5 天＋不可能目標＝第 5 天敗北路徑 ✓。管線健康。
- **但匯出打包的是誰？** 槽裡先放一座 60 天的城市 A（113 座建築），進編輯器開新圖、放 3 座公園、
  設好目標、按「📤 匯出場景分享碼」——**匯出包裡是城市 A 的 113 座建築**（帶著剛設的新目標）。
  手動存檔後再匯出才是正確的 3 座公園。

## 1. 根因

`buildEditorShareData()` 讀 `localStorage` 當前槽，而**匯出前沒有任何主動存檔**；
全遊戲唯一的自動存檔是 25 秒 wall-clock 定時器（T527）。所以：

- 進編輯器後 25 秒內匯出 ⇒ 打包**上一局的城市**（或空槽直接拒絕「目前槽是空的」——明明畫面上有圖）。
- 25 秒後匯出 ⇒ 永遠缺**最後一筆編輯到匯出之間**的內容（至多 25 秒的無聲丟失）。

玩家視角：「我編的場景，朋友打開是我上一局的城市。」`GV.editorExportCode()` 測試鉤同病。

## 2. 為什麼這張卡是安全的

`save()` 不在 tick 路徑（手動存檔按鈕、自動存檔定時器同一函式）；匯出鏈
（`exportEditorShare`／`buildEditorShareData`）只被 UI 按鈕與 GV 鉤子呼叫
⇒ 對模擬零影響 ⇒ **六哨兵位元恆等、不需重釘**。

## 3. 落地（兩刀，皆 offer/UI 側）

1. **匯出即所見**：`buildEditorShareData()` 讀槽前先 `if(tiles)save();`——
   UI 按鈕與 GV 鉤子兩條路一起修（單一修點；tiles 守門與自動存檔同款）。
   原註解「純記憶體操作，不落地 localStorage」隨之更正（它描述的是 egoal 打包，不是誰依賴的契約；
   落地當前世界正是玩家按「匯出」時以為發生的事）。
2. **幸福示例對齊 T539**：編輯器幸福目標的 prompt 示例「例如 0.78」與 fallback `||.78`
   改 **.72**——T539 已把 happy80 與 sc_harmony 對齊到實測可持續天花板 .72，
   編輯器還在建議 .78＝引導創作者做出接近不可能的場景（值-文案同步家族）。

**刻意不做**：不動 fail 打包（`fail.byDay`＝goal.byDay，勝負同日時勝利先判＝T132 既有順序）；
不動其他目標型別（pop 勝/敗已行為驗證，其餘與內建場景共用 T132 評估管線）。

## 4. 驗收計畫

- **G1（靈魂）匯出即所見＝行為釘**：套件裡世界 A（有建築）存檔 → 開新世界 B（不存檔）→
  `GV.editorExportCode()` 解碼 → 建築數必須等於**世界 B 當下**、不得等於世界 A。
- **G2 幸福示例同步**：原文釘「例如 0.72」在場、「例如 0.78」絕跡；fallback 與 happy80 目標值
  從源碼各自抽出比對相等（同步釘，不硬編碼第二份真相）。
- **G3 save 在讀槽之前**：`buildEditorShareData` 函式體內 `save()` 出現於 `localStorage.getItem` 之前（原文釘）。
- **G4 六哨兵位元恆等**（匯出鏈不在 tick 路徑）。
- 紅源：①拔掉 save() → G1 應紅；②守門寫死（`false&&tiles`）→ G1 應紅（條件死掉與拔除是不同失敗型）；
  ③示例改回 .78 → G2 應紅。
